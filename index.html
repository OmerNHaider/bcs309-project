Problem Overview

The Problem

Given n jobs, each with a processing time, and 2 identical machines, assign every job to one machine to minimize the makespan — the time when the last machine finishes.

Makespan = max(Machine 1 total, Machine 2 total)

We use 2 machines because that is the minimum needed to make the problem hard — and it directly connects to the Partition problem.

Why Is It Hard?

This problem is NP-complete. There is no known algorithm that finds the best schedule in polynomial time.

With n jobs and 2 machines there are 2n possible assignments. For 30 jobs that is over 1 billion.

So instead we use a greedy approximation (LPT) that runs fast and is provably close to optimal.

NP-Completeness Proof — Reduction from Partition

To prove a problem is NP-complete you need two things: (1) show a solution can be checked quickly, and (2) show that any other NP problem can be converted into yours. We do that below using the Partition problem.

Step 1 — Job Scheduling is in NP

A certificate is an assignment of each job to one of the two machines. A verifier sums up the processing times on each machine and checks if the maximum is ≤ D. This runs in O(n) time — polynomial. So the problem is in NP.

Step 2 — Reduction from Partition (m = 2 machines)

Partition: Given numbers a1,...,an with total sum 2T, can we split them into two subsets each summing to T?


Construction (O(n)): Create n jobs with pi = ai, use m = 2 machines, target D = T. Just copies n numbers — polynomial.

Forward Direction (Partition YES → Scheduling YES)

If S splits into S1 and S2 each summing to T, assign S1 to Machine 1 and S2 to Machine 2. Both loads = T. Makespan = max(T, T) = T = D. ✓

Backward Direction (Scheduling YES → Partition YES)

If makespan ≤ T, both machines have load ≤ T. Total load = 2T. The only way two values are each ≤ T and sum to 2T is if both equal exactly T. So the machine assignments are a valid partition. ✓

Why m = 1 is in P

With one machine, every job goes on it. There are no choices. Makespan = sum of all times. Just add them in O(n). The hardness comes entirely from having to choose which machine — with one machine that choice disappears.

Algorithm Design — Greedy Paradigm & Approximation Bound

This section explains what kind of algorithm LPT is and why it is not too far off from the best possible answer. The left side covers the "greedy" design pattern. The right side shows the math behind how close LPT actually gets.

LPT is a greedy algorithm
The greedy pattern from the course (Algorithmic Paradigms notes):
SORT(input)
for x in input_order:
   if FEASIBLE(x, state):
     TAKE(x, state)
     UPDATE(state)
LPT maps exactly onto this pattern:
SORT — Sort jobs largest to smallest (longest processing time first).
TAKE (locally optimal choice) — Assign the next job to the machine with the current minimum load. Never revisit this decision.
UPDATE — Add the job's time to that machine's load. Move to the next job.
Why it works reasonably well: Large jobs go first when machines are balanced. Small jobs fill gaps at the end. This prevents the worst-case imbalances.
Approximation bound for m = 2 machines

The General Formula

LPT makespan ≤ (4/3 − 1/(3m)) × OPT

For m = 2:   4/3 − 1/(3 × 2) = 4/3 − 1/6 = 8/6 − 1/6 = 7/6

LPT is never more than 16.7% worse than the optimal schedule on 2 machines.

Why the Bound Holds (Informal Argument)

Consider the last job to finish — job j with time p. When LPT placed it, it went to the less-loaded machine (load L). The other machine had load ≥ L.

Total job load = S. Both machines share it, so L ≤ S/2.

LPT makespan = L + p ≤ S/2 + p.

Job j is the smallest (sorted last), so p ≤ OPT/m. Combining these inequalities leads to the 7/6 bound for m = 2.

Tight Example (Ratio = Exactly 7/6)

Jobs [3, 3, 2, 2, 2] on 2 machines:

LPT makespan = 7  |  OPT makespan = 6

Ratio = 7/6 ≈ 1.167 — hits the bound exactly.

No input on 2 machines can produce a worse LPT ratio than 7/6.
