The Problem

Given n jobs, each with a processing time, and 2 identical machines, assign every job to one machine to minimize the makespan — the time when the last machine finishes.

Makespan = max(Machine 1 load, Machine 2 load)

Why Is It Hard?

This problem is NP-complete. No known algorithm finds the optimal schedule in polynomial time.

With n jobs there are 2n possible assignments. For 30 jobs that is over 1 billion.

Our Approach

We use LPT (Longest Processing Time first) — a greedy algorithm that runs in O(n log n) and is never more than 7/6× worse than optimal for 2 machines.

1  —  NP-Completeness Proof & Reduction from Partition

To prove NP-complete: (1) a solution can be verified quickly, and (2) a known NP-complete problem reduces to ours in polynomial time.

Step 1 — Job Scheduling is in NP

A certificate is an assignment of jobs to machines. A verifier sums the times on each machine and checks if the max is ≤ D. This is O(n) — polynomial. So the problem is in NP.

Step 2 — Reduction from Partition

Partition: Given numbers a1,...,an summing to 2T, can we split them into two subsets each summing to T?

Construction O(n): Create n jobs with pi = ai, m = 2 machines, target D = T. Just copies the numbers — polynomial time.

Forward — Partition YES → Scheduling YES

If S splits into two halves each summing to T, assign one half to each machine. Both loads = T. Makespan = max(T, T) = T = D. ✓

Backward — Scheduling YES → Partition YES

If makespan ≤ T, both machines have load ≤ T. Total load = 2T. The only way two values are each ≤ T and sum to 2T is if both equal exactly T. So the assignments form a valid partition. ✓

Why m = 1 Is in P

With one machine there are no choices. Makespan = sum of all times. Compute the sum in O(n). The hardness comes entirely from choosing which machine to assign jobs to.

2  —  LPT Algorithm Analysis & Approximation Bound

Why LPT is a greedy algorithm and how we know it is never more than 7/6× worse than optimal for 2 machines.

LPT is a greedy algorithm

The greedy pattern from the course:
SORT(input)
for x in input_order:
  if FEASIBLE(x, state):
    TAKE(x, state)
    UPDATE(state)
LPT maps exactly onto this:
SORT — Sort jobs from largest to smallest processing time.
TAKE — Assign the next job to the machine with the smallest current load. Never go back.
UPDATE — Add the job's time to that machine's load. Move to the next job.
Why it works: Large jobs go first when machines are balanced, so small jobs fill any gaps at the end without creating big imbalances.

Approximation bound — m = 2 machines

General Formula

LPT makespan ≤ (4/3 − 1/(3m)) × OPT

For m = 2:  4/3 − 1/6 = 7/6 ≈ 1.167

LPT is never more than 16.7% worse than the optimal schedule.

Why It Holds

The last job placed (the smallest one) goes to the less-loaded machine. That machine's load before placement is ≤ half the total job sum. The smallest job size is ≤ OPT/m. Combining these gives the 7/6 bound.

Tight Example — Ratio = Exactly 7/6

Jobs [3, 3, 2, 2, 2] on 2 machines:

LPT = 7  •  OPT = 6  •  Ratio = 7/6 ≈ 1.167

No input with 2 machines can do worse than this ratio.
